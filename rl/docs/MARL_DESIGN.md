# 分层 MARL 设计：全局调度网络 + 单车行驶网络

> 前提：单场景到多车竞争的现有成果（四档课程、四档成功率）作为 **level-1 基线**保留，本文档描述在其之上加一层全局调度（level-2）的设计。
> 目标不是"堆一个新架构"，而是**用一个可对照的实验回答：学出来的调度是否比人工调度更好**。

---

## 1. 问题重述：把"车辆价值"换成"配对价值"

原始直觉是"给每辆车算一个调度价值，取 top-k 送进调度网络"，于是遇到三堵墙：可变长、价值定义靠人工、远距离车辆的共同价值无法用局部输入表达。

**根因**：全局价值不是某辆车的属性，而是**（车，任务）配对**的属性。

出租车任务的调度本质是一个**分配问题**：

```
输入：N 辆车（状态各异、有的载客有的空驶） × M 个待接乘客（位置、等待时长、是否被对手争抢）
输出：一个匹配（每辆车至多接一单，每个乘客至多被一辆车接）
目标：最大化全局收益（送达数 / 最小化等待时间 / 最小化空驶里程）
```

三点立刻通畅：

| 原困惑 | 换成"配对 + 匹配"之后 |
|---|---|
| 阵营车辆数可变 | N、M 天然可变，匹配算法不要求定长；网络侧用 padding + mask |
| "什么车有价值"要人工定义 | 不定义车辆价值，网络只输出配对的**分数**，全局最优由匹配求出 |
| 远距离车辆的共同价值 | 它们共同体现在**争抢同一个任务**上，匹配的目标函数本身就是全局的；两车争一客时会自动分派一个、另一个转去远单 |

**启发式基线其实你已经有**：`PassengerDistributeManager.pick_best_target_for()` 就是一个人工调度器（最近乘客 + 预约锁）。level-2 要做的事情，本质上就是**把这个函数换成学出来的**——改造点干净、对照实验现成。

---

## 2. 架构：三选一（推荐 A）

### A. 双塔分数 + 掩码匹配（推荐，O(N·M) 且落地最快）

```
                  ┌────────────── 车辆编码（复用/共享） ──────────────┐
  车 i 局部观测 ──►│ 现有 CombinedExtractor ──► 384 ──► φ(v_i) ∈ R^64 │
                  └──────────────────────────────────────────────────┘
                  ┌────────────── 任务编码 ──────────────────────────┐
  乘客 j 特征   ──►│ MLP ──► ψ(t_j) ∈ R^64                            │
                  └──────────────────────────────────────────────────┘
  score[i,j] = φ(v_i)^T · W · ψ(t_j)          # 双线性，O(N·M)，天然置换不变
  score[mask] = -inf                          # 载客中 / 已占用的乘客 / 不可达
  assignment = Hungarian(score)               # 或 Sinkhorn（可微，端到端）
  → 每辆车拿到目标乘客索引（作为 level-1 的指令通道）
```

优点：参数量小、不需要定长、置换不变、**远距离耦合自动被全局最优处理**、匹配可换成 Sinkhorn 做端到端。

### B. 加一层全局注意力（A + 协作项，仍很便宜）

在 A 的双塔之上，对车辆 token 与任务 token 各做 1–2 层 masked self-attention，再加一个**学习的 CLS query** 做池化：

- CLS 与全体车辆做一次 cross-attention，成本 `O(N·d)` ——**线性**，这就是"远距离车辆共同价值"的捕获方式，不需要 O(N²)；
- 车辆之间做一层 self-attention，成本 `O(N²)`，N≤16 时可忽略。

这版对应你原来的"窗口"直觉：**query 学出来，而不是人工算价值**（= Set Transformer / Perceiver 的 latent bottleneck 思路）。

### C. 完全 Transformer

只有当需要长时域跨车推理时才考虑；用 Perceiver 式 latent bottleneck 或线性注意力把复杂度压到 O(N·M)。**当前规模（4 车/阵营、N≤16）没有必要**，先不要上。

### 关于实时性（估算，供答辩引用）

| 模块 | 量级 |
|---|---|
| 单车射线塔（共享 Conv1d）+ 线性层 | ≈ 20 万 MACs |
| MLP[256,256]（384 维输入） | ≈ 16 万 MACs |
| 全局注意力（N=16, d=64, 3 层） | ≈ 20 万 MACs |

**加一个全局调度块 ≈ 一辆车自身编码器的成本**，而真正的时间开销在 240 Hz × 车辆数的物理推进上。
再加**双时间尺度**：调度每 0.5–2 s（8–16 个决策步）出一次指令，行驶策略每步跑。这就是 options / FeUdal manager-worker 的标准结构（FeUdal Networks 的 manager 输出目标，worker 执行）。

## 3. 具体输入设计（可直接实现）

### 3.1 车辆 token（每车，固定长度）

| 组 | 维度 | 内容 |
|---|---|---|
| 局部编码 | 64（投影自 384） | 复用现有 `CombinedExtractor` 的输出 |
| 业务状态 | 3 | 是否载客 / 是否已被分配 / 距回合上限剩余比例 |
| 位置 | 3 | 归一化 (x, z) + 朝向 |
| 运动 | 3 | 速度向量 (vx, vz) + 速率 |
| 局部任务线索 | 3 | 最近**未分配**乘客的相对位置 (2) + 距离 (1) |

**关键缺口（必须先补）**：现在的观测里只有**对手**通道（`RivalPositionSensor` 6 辆 × 4 维），**没有队友状态**。调度器是阵营级的，必须能看到队友。新增一个与对手通道同构的队友通道（位置 x/z、距离、是否载客），或者在调度器输入里单独拼——前者对 level-1 也更有用（避免两辆车同时扑同一个乘客）。

### 3.2 任务 token（每个待接乘客）

位置 (x, z)、等待时长（归一化）、目的地相对位置 (2)、是否已被预约、**最近的对手距离**（判断是否被抢）、任务"年龄"分箱。

### 3.3 输出与下发

- 输出：`score[i, j]` → 匹配 → 每辆车一个目标乘客索引；
- 下发：动作空间加一维（或用独立的 command 字段）作为**目标覆盖指令**；`AITaxiContorller.set_action()` 里已有目标选择逻辑，把 `PassengerDistributeManager.pick_best_target_for()` 的返回值替换成外部指令即可（保留"无指令时回退到启发式"的开关，便于做对照）。

## 4. 训练配方（按风险从低到高，逐步升级）

**阶段 0（1–2 天）**：固定 level-1 权重，只训调度器。
- 只更新双塔/注意力参数，level-1 冻结；
- 奖励：团队总收益（送达数增量）减去等待时间惩罚，权重先用手调小值；
- 目的：先验证"学出来的配对分数 ≥ 最近乘客启发式"，这是最容易拿到的正结果，也是论文里最干净的一张对照表。

**阶段 1**：CTDE 联合微调（MAPPO 风格）。
- 集中式 critic 看全局（所有车辆 + 乘客），actor 只用局部观测；
- level-1 用小学习率（如 1e-4 起，或直接冻结共享层只调调度器）；
- 注意：level-1 的行为在变，level-2 的目标分布跟着变 = **非平稳**，所以要监控"分配达成率"（分配了但没接到的比例）。

**阶段 2**：信用分配精细化。
- QMIX / VDN 式的价值混合，或反事实基线（某辆车的贡献 = 团队收益 − 去掉它之后的收益估计）；
- 调度器的优势 = 团队优势 − 个体优势之和，避免"调度器抢了行驶策略的功劳"。

**必须做的一件事：把 level-1 冻结时的调度器作为主结果**，联合训练作为加分项。层次化 RL 的非平稳性很容易把两个网络一起训崩，而你时间有限。

## 5. 对照实验（论文的核心贡献在这里）

| 编号 | 调度器 | 说明 |
|---|---|---|
| B0 | 最近乘客（现有启发式） | 现成基线 |
| B1 | 最近乘客 + 预约锁 | 现成基线（当前实际行为） |
| B2 | 竞价（bid = −ETA） | 经典多智能体分配 |
| B3 | 真值距离的匈牙利匹配 | **上界参考**（会 oracle 一点，用于判断学习差距来自分数还是匹配） |
| M1 | 学习配对分数 + 贪心 | 拆开看匹配算法贡献 |
| M2 | 学习配对分数 + 匈牙利 | 主方法 |
| M3 | M2 + 全局注意力 | 看注意力是否带来增益 |

**指标（业务指标，不用奖励值）**：送达成功率（带判据）、平均乘客等待时间、空驶里程占比、抢客成功率、**分配达成率**。
每个结果都必须连同**判据 + 阵营数 + 并行智能体数**报告（沿用 level-1 的纪律）。

## 6. 风险与对策

| 风险 | 对策 |
|---|---|
| 层次化非平稳，两层一起训崩 | 先冻结 level-1 只训调度器；联合训练时给 level-1 小学习率并监控分配达成率 |
| 调度器与行驶策略"打架" | 指令要软性（目标 + 未达成即可重新分配），并且保证 level-1 的事件奖励与指令方向一致 |
| 学出来的分数退化回"最近乘客" | 检查分数矩阵与距离的秩相关；若高度相关说明任务 token 特征不足（补等待时长、被抢风险、方向一致性） |
| 车辆数泛化差 | 训练时随机化 N（如每局随机 2–6 车/阵营），用 mask 训练；评估 N 超出训练范围 |
| 观测里没有队友信息 | 先补队友通道，再训调度器（否则调度器只能靠猜） |
| 匹配不可微、梯度传不进去 | 用 Sinkhorn 软化，或 Hungarian 只作为解码器（分数网络用决策后的回报做 REINFORCE 式更新） |

## 7. 与超算的配合（工程侧）

- Godot 侧已是**无头可跑**（`MultiFlatWallTrain.exe` + `.pck`），超算上按进程数横向铺开即可；调度器在 Python 侧前向，不增加仿真侧成本。
- 一个仿真进程负责若干场地，`n_parallel` 决定并行环境数；**调度器需要同一阵营的车辆在同一进程内**（否则要跨进程通信），这在设计场地分配时要先定下来。
- 训练配置一律走命令行参数 + 场景文件，保持"训练/评估/演示同配置"（物理步长一致）的纪律。

## 8. 建议里程碑

| 里程碑 | 内容 | 判定 |
|---|---|---|
| M0 | 补队友观测通道；把调度器接口做成"可覆盖的指令" | 单场景跑通，无指令时回退启发式行为不变 |
| M1 | 冻结 level-1，训双塔分数 + 匈牙利 | 在平均等待时间或送达数上 ≥ B1 |
| M2 | 加全局注意力（CLS query 池化） | 相对 M1 有增益（同判据同种子） |
| M3 | 随机 N 训练，评估变长泛化 | N 超出训练范围仍不退化 |
| M4 | CTDE 联合微调 | 多车成功率相对 10.5% 基线明显提升 |
