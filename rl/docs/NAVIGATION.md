# 全局导航 + 局部避障：低成本方向

> 结论先行：**全局规划用引擎内置的精确算法（一次性/低频），RL 只负责"把导航意图在动态环境里变成可行动作"。**
> 你现在的势函数塑形其实已经是一个"局部导航场"，它有已知缺陷（非凸障碍下的局部极小），所以缺的是**全局一致性**，不是"更强的网络"。

---

## 1. 先把问题说清楚：为什么纯 RL + 射线做不了导航

- 射线提供的是**局部、反应式**信息，它回答"现在往哪打方向不会撞"，不回答"绕过这堵墙该走哪边"。
- 你现在用的 `rw_progress × (d_prev − d)/d_0` 是**基于欧氏距离的势函数**。这正是经典人工势场法：在非凸障碍（墙）面前，它的极小值出现在墙面上，而不是目标点。
- 你已经用实测数据见过这条曲线：停车 ≈ −23 / 回合，硬闯障碍 ≈ −142，停准送达 ≈ +10。当时把它归因为"奖励结构问题"，但**几何上的局部极小是同时存在的**。
- 于是纯 RL 方案被迫用大量样本去"试出"绕行路线，这既慢又不可复现（六种场地变体只到 44–60% 就是代价）。

**所以要做的不是换更大的网络，而是把"全局一致性"这件事交给一个能精确计算的层。**

---

## 2. 三层结构（推荐）

```
第一层：全局规划（静态地图，一次性/低频/精确）
   场地墙面栅格化 → A* → 折线路径 → 视线捷径简化 → 3~5 个路点
        ↓ 路点序列
第二层：引导表示（喂给 RL 的形式，不是硬约束）
   lookahead 路点相对坐标 + 横向偏差 + 航向偏差 + 路点进度
        ↓
第三层：局部控制（RL 负责）
   油门/转向/倒车 + 动态避让（其他车，非合作）+ 停稳精度 + 倒车脱困
```

**关键设计原则：规划器给"参考"，不给"枷锁"。** 路点作为**观测**喂进去，RL 可以为了避让偏出去、之后再回到路径上。如果把它做成"必须沿路径走"的硬约束，RL 就只剩下跟踪控制器的作用，你的工作会失去价值（也会被老师追问"那 RL 做什么"）。

---

## 3. 最省成本的实现（约 80 行 GDScript）

你的场地是 **200×200 平面 + 轴对齐 `BoxShape3D` 墙**，且**墙是静态的**——这意味着：

| 方案 | 成本 | 评价 |
|---|---|---|
| **`AStarGrid2D` + 墙栅格化**（推荐） | 约 80 行；0.5–1 m 网格 → 4 万格；查询约 1 ms 且低频 | **最省、最精确、可复现**；轴对齐盒子直接按 AABB 涂格 |
| `NavigationRegion3D` + 烘焙 navmesh | 0 行代码，但烘焙慢、薄墙（1 m）边缘易出误差 | 备选；几何变复杂（坡道、多层）时再换 |
| 自建可见性图 | 精确但要做多边形裁剪 | 代码量大于栅格 A*，不值得 |
| 人工摆路点 | 最省，但不泛化 | 只适合当课程脚手架，不能当交付物 |

**实现要点**
1. **场景加载时烘焙一次**：遍历 `StaticBody3D` 的 `BoxShape3D`，把 AABB 内的格子标为不可通行（车宽约 2 m → 障碍膨胀半车宽，这一步别忘，否则路径贴着墙过）；
2. 查询触发条件：目标变化时、每 K 帧、**以及卡死检测触发时**（见第 5 节）；
3. 路径简化：从起点开始做**视线捷径**（沿线采样查是否碰撞），把 A* 的锯齿折线压成 3–5 个路点；
4. 路点不用换得太勤：取"离车最近但已越过"的下一个路点作为当前目标即可。

---

## 4. 最高性价比的单点改动：势函数从"直线距离"换成"沿路径剩余弧长"

这一处改动同时解决两件事，**建议优先做**：

```
现在： Δpotential ∝ (∥goal − p_prev∥ − ∥goal − p_now∥)     ← 非凸时出现假的极小值
改成： Δpotential ∝ (s_prev − s_now)                        ← s = 沿路径的剩余弧长
```

- 势函数变成"沿路径的进度"，**在路径上单调**，局部极小消失，"停车"不再有任何潜在收益；
- 换布局不用重调参数的性质保留（仍然按本段初始值归一化）；
- **实现坑**：车为了避让偏离路径后，投影点可能跳变。投影搜索要**限制在上一帧投影点附近的窗口内**（如 ±10 m），这是 pure pursuit / 横向误差控制器的经典 bug。

---

## 5. 喂给 RL 的引导表示（建议 10 维，替换 v2 契约里的"目标 6 维"）

| 内容 | 维度 |
|---|---|
| lookahead 路点相对坐标（当前 + 下一个 + 再下一个） | 6 |
| 横向偏差（车到路径的垂距，归一化） | 1 |
| 航向偏差（车头与路径切线夹角） | 1 |
| 到当前路点的相对速度（或沿路径投影速度） | 1 |
| 路点进度 / 剩余路点数（归一化） | 1 |

于是观测契约 v3 ≈ `8 自车 + 384 射线 + 10 引导 = 402`。

**卡死恢复**：加一个"N 步内沿路径弧长进度 < 阈值"的检测 → 触发重新规划或倒车脱困。你的动作空间本来就有倒车通道和 4 步滞回，这个机制几乎零成本，而且**直接复用你已经踩过的"冻结均衡"诊断经验**。

---

## 6. 必须做的对照实验（这才是"价值"的来源）

| 编号 | 系统 | 目的 |
|---|---|---|
| **B0** | A* 规划 + 纯跟踪（Pure Pursuit）+ 固定速度 | **经典基线。必须做** |
| B1 | A* + 纯跟踪 + RVO/`NavigationObstacle3D` 动态避让 | 更强的非学习基线 |
| B2 | 纯 RL + 欧氏势函数（现状） | 你已有的 0.965 / 44–60% / 10.5% |
| **M1** | A* 路点作观测 + RL 局部控制（本方案） | 主方法 |
| M2 | M1 + 倒车脱困 + 卡死重规划 | 完整版 |

**指标**：送达成功率（带判据）、平均到达时间、路径长度与转向平滑度、**卡死率（局部极小次数/回合）**、空驶里程。

**预期结果（也是你的核心论点）**：B0/B1 在空场地会很强，但会在四个地方明显掉下来——
1. **动态、非合作的交通**（对手车不会让路；B1 的 RVO 只做无冲突分解，不做博弈）；
2. **停稳精度**（判据要求 1.5–2.5 m/s 内停住且停在 2–3 m 半径内，纯跟踪很容易超调）；
3. **倒车脱困**（被顶住、死胡同，经典跟踪器没有这个能力）；
4. **执行器与动力学约束**（扭矩转换器、换挡、转向迟滞——你的车不是差速小车）。

**这四条就是"为什么需要 RL"的答案**，也是你这个项目最有说服力的地方：RL 的价值不在"会导航"（精确算法做得更好），而在"把导航意图在动态、非合作、有执行器约束的环境里变成可行动作"。

---

## 7. 更贵、但更有论文价值的方向（现在别做）

1. **特权教师蒸馏**：把 A* 当教师，让策略额外预测下一个路点（辅助任务），甚至蒸馏出一个不需要规划器的策略。
   价值：可以讲"学习式全局导航"。风险：很可能被追问"这不就是学了个 A*"，而且额外工作量不小。**放到 P6 之后**。
2. **学习式代价地图**：保留经典规划器，只学习"哪些区域代价高"（拥堵、被抢客风险）。
   价值：调度与导航的耦合点很自然。风险：两层学习耦合，非平稳性上升。**留作未来工作**。
3. **端到端地图条件策略**：把局部占据栅格喂给网络，让 RL 自己学导航。
   最贵、最不稳、最需要样本。你现在有超算，但**收益/风险比最差**，不建议作为主线。

## 8. 附：事件触发式单查询规划（Informed RRT*）+ RL 参考跟随 —— 成立性审计

**结论：架构成立（这就是"全局规划器 + 局部控制器"的标准形态），而且"事件触发重规划"的频率选得对。缺的是四项考量，其中第 1、4 项会在训练中直接踩坑。**

### 先说为什么成立

| 你的设计 | 为什么对 |
|---|---|
| **每次任务事件生成一次路径**（去接客 / 去送客 / 目的地变更） | 频率选得对：不是每帧（避免移动靶），也不是"烘一次永不变"（无法适应任务变化）。**事件触发是正确的时间尺度。** |
| 用**单查询**规划器（Informed RRT*） | 单查询规划器就是为"一次 (起点, 目标)"设计的；目标已知时 informed 版本能用椭圆收窄采样区域，收敛更快 |
| 路点只作**参考**，允许不重合 | 保住了 RL 的价值空间（动态避让、动力学、停稳精度），没把它降级成路径跟踪器 |
| 免烘焙、任意几何可用 | 对**程序化 / 新地图**天然可用，不用为每张图手工布点或烘焙 |

**一点澄清：你之前定的"静态地图"约束是"不要动态重建地图"，不是"不许重规划"。** 按任务事件重规划与之完全兼容。

### 缺的考量 1：随机性管理（**最容易踩**）

RRT* 是随机的：同一 (起点, 目标) 两次查询给出不同路径。后果：
- **训练/评估分布漂移**：策略训练时见过的参考路径族与评估时不同 → 你"同配置"的纪律在参考信号这一层被破坏；
- **调试困难**："这次失败是策略的问题还是路径的问题？"

三种处理方式（按推荐）：
1. **按任务冻结路径**：路径一旦为某个任务生成就固定不变，直到任务结束或触发重规划条件。**绝不要每个决策步重算**；
2. **固定种子 + 缓存**：同一任务重复查询返回同一条路径；
3. **把随机性当域随机化（正面利用）**：训练时每个 episode 用不同种子的路径，评估时固定种子 → 策略对参考路径的细微变化更鲁棒。**这一条可以写进论文**（"参考路径随机化提升鲁棒性"）。

### 缺的考量 2：重规划触发条件要列全

你只说了"目的地变化"。完整清单：

| 触发 | 说明 |
|---|---|
| 任务事件 | 接客 / 送达 / 目的地变更 ✅ 你已有 |
| **偏离超阈值** | 车为避让绕出去 20 m 后旧路径已不是好参考 → 重规划，或让 RL 回路径（**二选一，必须定死**） |
| **卡死检测** | N 步内沿路径弧长进度 < 阈值 → 重规划 + 倒车脱困 |
| 环境变化 | 将来若有可破坏物 / 路障 / 玩家放置障碍，地图就不再静态 |
| ❌ 每物理帧 / 每决策步 | 不要 |

**"偏离后是重规划还是回路径"不明确，行为就会摇摆**（一会儿重规划、一会儿回路径），RL 学到的是噪声。

### 缺的考量 3：给车用的路径，后处理三件套躲不掉

采样规划器输出的原始路径是**折线 + 随机抖动**，直接给车用会更糟：

1. **曲率可行**（最小转弯半径 / 平滑）——RRT* 原始路径常带急折角，RL 会被学成抖动；**采样路径比栅格路径更需要平滑**；
2. **净空**（离墙 ≥ 车半宽）——采样规划器同样要做障碍膨胀或净空检查（采样到离墙 0.3 m 的点是常事）；
3. **等间距重采样 + lookahead 选取**（喂给 RL 的形式要统一）。

所以"用 RRT* 省掉后处理"不成立——**它反而增加平滑的工作量**。

### 缺的考量 4：偏差奖励的形式（"允许不重合"要落成公式）

```
r = w_progress * Δs                            # 沿参考路径的弧长进度（正）
  − w_cross   * max(0, |e_cross| − dead_zone)  # 横向偏差，带死区
  − w_head    * |e_head|                       # 航向偏差
```

三条纪律：
1. **横向偏差用带死区的软惩罚**（例如 |e| < 1.5 m 不罚）。硬惩罚或零死区会让 RL 为了贴合路径而**放弃避障**；
2. **避障优先级必须高于贴合路径**——权重上确保"为了避让而偏离"是净收益；
3. **偏差持续超阈值 N 步 → 判定"参考路径失效"并触发重规划**，而不是继续加惩罚（否则车会僵在两条路之间）。

### 缺的考量 5（工程）：规划器放哪一侧、性能如何

- **路径一定要在 Godot 侧生成**（事件触发），lookahead 特征作为观测的一部分发给 Python。**不要在 Python 训练循环里做规划**，跨进程传路径会污染训练管线；
- **GDScript 里实现 RRT\* 要有性能心理准备**：迭代与碰撞检查都在脚本层，实测可能是引擎内置 `AStarGrid2D`（C++）的数百倍。事件触发下一次查询花 50–200 ms 通常可接受（任务切换时的小卡顿），但**必须先测量**。

### 最重要的一条建议：把规划器做成**可替换接口**

你的架构（**事件触发 + 参考路径 + 允许偏离的局部 RL**）与"用哪个规划器"是**正交**的：

```
NavPlanner（接口）
  ├── GridAStarPlanner        # 确定性、极快、现在就能用
  ├── InformedRRTStarPlanner  # 任意几何、无需预处理、随机
  └── HybridPlanner           # A* 出初解 → informed RRT* 在椭圆内精化
```

三个好处：① **RRT\* vs A\* 从"必须提前押注"变成"对照实验"**（正是论文需要的）；② 现在就能用 A* 把整条链路（路径 → lookahead → RL 观测 → 弧长势函数）跑通，不必等 RRT* 调好；③ 想上 RRT* 时只换一个类，观测维度与奖励设计完全不动。

### 评估设计（证明"参考路径有用"）

- **A/B**：纯 RL（无路径）vs RL + 参考路径 → 成功率、平均到达时间、**卡死率**；
- **消融**：RRT* 迭代预算 100 vs 1000（路径质量）→ 策略是否对路径质量敏感；
- **鲁棒性**：训练时路径随机化 vs 固定种子 → 评估时换一批种子，看退化幅度。

---

## 9. 一句话总结

**把"绕不绕得过去"这件事交给精确算法（引擎内置 A*，约 80 行、一次性烘焙、静态地图），把"在动态对手、执行器约束、停稳精度下的动作选择"留给 RL；再顺手把势函数从直线距离换成沿路径弧长，一处改动消掉局部极小。** 这样你既拿到了全局导航能力，又保住了 RL 的价值空间，而且成本极低。
