# 方向决定版：level-1 重建 → 调度器 → 炮台

> 依据：`rl/docs/MARL_DESIGN.md`（架构论证）+ godot_rl 0.8.2 源码（桥接机制核实）。
> 本文档只写**决定**，不写备选方案。

---

## 0. 三个已核实的事实（决定了方案边界）

1. **SB3 训练路径只支持单策略。** `stable_baselines_wrapper.py::_check_valid_action_space()` 明确检查 `action_space` 必须是单个空间，多于一个直接抛异常；`core/godot_env.py` 里 `action_spaces / observation_spaces / agent_policy_names` 是**每个 agent 一份**，注释写着多智能体只对 Rllib 开放。
   → **"同时训练两个 RL 算法"在 SB3 路径上做不到**，也不需要做（你的直觉是对的：会难收敛）。
2. **所有 agent 的观测是拍平的一维批次。** wrapper 里 `num_envs = agents_per_process × n_parallel`，`obs = lod_to_dol(all_obs)`，所以 `obs["obs"]` 形状是 `(总 agent 数, 419)`；动作按 `action[i*n:(i+1)*n]` 切回各进程，再按 agent 拆成 `{policy_name: value}` 字典发给 Godot。
   → 要做阵营级调度，**必须在 Python 侧把扁平批次 reshape 回 `(场地数, 每阵营车辆数)`**，而 reshape 需要 Godot 侧给出**稳定的 agent 顺序 + 有效掩码**。
3. **info 默认是 `[{}] * len(done)`**（`step_recv` 第 215 行），这就是当初 `task/pickups` 恒为 0 的根因。
   → 场地/阵营/槽位这类结构化上下文，要么进 `info`（继续扩展你写的 `_patch_godot_env_info`），要么直接进观测。

## 1. 决定一：重建 level-1，先把单车开好

**观测契约 v2（419 → 398）**

| 段 | v1 | v2 | 说明 |
|---|---|---|---|
| 自车状态 | 8 | **8** | 不变；后续加 `health` 再升到 9 |
| 射线感知 | 384 | **384** | 不变；碰撞规避仍由射线承担 |
| 目标（被分配的乘客/目的地） | — | **+6** | 相对位置 3 + 相对速度 3（或 + 距离/朝向凑 6） |
| 对手 6 辆 × 4 | 24 | **扣掉** | 竞争判断归调度器；这 24 维让观测依赖车队规模 |
| 乘客目标 3 | 3 | **并入目标段** | — |
| **合计** | 419 | **398** | — |

**为什么可以扣（这不是偷懒，是分层的前提）**
- 反应式避碰由射线完成（射线本来就带类别，车辆是一个类别）；
- "谁离乘客更近、谁在载客"属于**阵营级信息**，是调度器的输入，不是行驶策略的输入；
- 扣掉之后**观测与车队规模无关**——这正是可变长调度能在上面成立的前提；
- **`RivalPositionSensor` 不要删**，只是从行驶策略的观测里"改道"到调度器的输入（调度器必须知道谁在抢同一单）。`observe_same_company` 默认 `false`，队友通道要另开一个实例（第二个传感器，别挤对手槽位）。

**必须做的验证**：把"扣对手通道"当成一次消融实验跑墙场景与多车场景（对比 96.5% 与 10.5% 基线）。别假设不影响——墙场景里的窄道会车是唯一可能退化的地方。

**倒车专属课程（你说要先学会移动+倒车）**
- 现有动作空间已含倒车通道 + 4 步滞回，`--action_bias "0,0,-0.5"` 先验也在；
- 新增一个"目标在车后/死胡同停车"的场地变体，专练倒车；
- 验收指标用你已经在打印的**倒车占比**：空场地正常任务应低（<5%），倒车专项任务应显著 >0，两者不能共用同一套判定。

**回归评测套件（先建这个，再动架构）**
固定种子 + 固定场景集（空场 / 墙 / 六变体 / 多车），每个场景记录 `success_rate / ep_len / pickups / dropoffs / 倒车占比 / 平均等待时间`，一键跑完出一张表。
理由：接下来要连续改架构，没有它你无法判断"这次改动是变好还是变坏"。

## 2. 决定二：调度器怎么拿到观察值

**桥接层不需要改协议**：Godot 已经把每个 agent 的 obs 都发过来了（就是同一批 398 维），调度器要的是**同一批数据的另一种组织方式**。

Python 侧的组装流程：

```
obs["obs"] 形状 (n_parallel × agents_per_process, 398)
   ↓ 按 Godot 侧的 agent 顺序 reshape（顺序必须固定且可查）
(n_parallel × arenas_per_process, vehicles_per_arena, 398)
   ↓ 按 company_id 分组（阵营身份来自 info 或观测里的 faction 通道）
(场地, 每阵营车辆数, 398)  →  调度器输入
   ↓ 输出：每个槽位的目标乘客索引（-1 = 不分配）
   ↓ 广播回扁平批次 → 作为"指令通道"拼进行驶策略的观测
```

**三个必须落实的接口约定**
1. **agent 顺序必须显式化**：目前顺序由 Godot 侧 `AIController` 的枚举顺序决定，属于隐性依赖。要么在 `info` 里回传每个 agent 的 `(arena_id, company_id, slot_id, alive)`，要么在观测里加 faction/槽位通道。**不要靠"应该就是这个顺序"**。
2. **掩码**：车厢数可变（训练时随机 2–6 车/阵营），必须有 `alive/valid` 掩码，无效位在注意力里 mask 掉。
3. **`vehicles_per_faction` 现在是 2，必须提高**（建议 4–6）。调度器只调度 2 辆车的话，学出来的调度与"最近乘客"的差别几乎无法在指标上体现——你的对照实验会做不出显著性。

**训练方案（一个算法，不是两个）**
- **不建议**两个 PPO 实例各自更新（非平稳 + 调试成本高）；
- **建议**先"冻结 level-1，只更新调度器参数"的**阶段式单算法训练**：
  - 若走 SB3：自定义 `ActorCriticPolicy`，`forward` 里做「每车编码 → reshape 成阵营 → 调度器 → 指令广播回每车 → 动作头」，用参数组把 level-1 的 `lr` 设为 0（或只把调度器参数交给优化器）。这是**一个 PPO、两个头**，不是两个算法。
  - 若不想动 SB3 的 policy：调度器也可以做成**回合级学习器**（用团队回报做 REINFORCE，或小参数量的进化策略），每次更新间隔若干个 episode。它天然与行驶策略解耦，非平稳性最小。
- 走哪条由你定，但**第一条路线（单 PPO 双头 + 冻结）是主推**。

## 3. 决定三：炮台（索敌与开火的分工）

**分工原则：能算的精确算，不能算的学习。**

| 环节 | 归属 | 理由 |
|---|---|---|
| 索敌（视距/角度/遮挡/LOS 判定出"范围内敌人列表"） | **算法**（Godot 侧射线/角度查询） | 这是几何判定，精确、O(K)、可复现；学它纯属浪费样本 |
| 选择打谁 | **学习**（策略输出目标槽位） | 涉及威胁评估、优先级权衡，人工写规则就是"人工参与过多" |
| 开关炮台 / 是否开火 | **学习**（策略输出开火位） | 与行驶动作耦合（追击、逃逸、绕后） |
| 敌人列表本身 | 观测中的**定长 K 槽位 + 掩码** | "范围内敌人"天然有上界，**炮台这里没有可变长问题** |

**射程内的敌人列表是天然定长的**：设 K=4，每槽 `[相对位置 3, 相对速度 3, 距炮口角度 1, 血量 1, in_range 1, valid 1]`，无效槽置零并 mask。这比调度器的可变长简单得多。

**动作空间（两种实现，先做第一种）**
1. **连续 + argmax（先做）**：`Box(-1,1,(3 + K + 1,))` = 行驶 3 通道 + K 个目标槽评分 + 开火位；Godot 侧对 K 个槽取 argmax 得目标。**协议不用改**，`TaxiSync` 的数组直接多几位。
   代价：不是真正的 categorical 分布，探索略糙（小 K 下实测可接受）。
2. **MultiDiscrete + MultiBinary（后面再上）**：分布更干净，但需要改 `TaxiSync` 的动作拆包（现在只支持单个空间），且 SB3 的 Dict/Tuple 动作空间在 `godot_rl` 的 SB3 wrapper 里是被检查拒绝的——**必须自己写 wrapper**。收益不值得现在付。

**配套改动**
- 观测加 `health`（自车）+ 受伤/被击毁事件进 `info`；
- 回合终止条件新增"被击毁"，`reset_after` 不变；
- 奖励用现有 `RewardManager` 分项：击伤/击毁（正）、被击中（负）、误伤队友（重罚）、开火弹药约束（可选）。**开关与参数照旧在出生时注入**，这套机制已验证，别改。
- **敌方策略先脚本化**（巡逻/追击/开火规则），自博弈留到后面。原因：敌方也学习会立刻把问题变成非平稳多智能体——那是另一篇论文的工作量。

**复用点**：调度器"车×乘客配对打分 + 匹配"的那套模块，**原样复用到"炮台×敌人"目标选择**上。一次实现，两处收益。

## 4. 决定四：空间划分——现在不做四叉树

**结论：暂不做。** 理由与替代方案：

1. **规模不到**。每场地 4 车、每阵营 2（未来 4–6）、乘客数在十量级。暴力两两比较 `O(N²)` 在这个数量级就是几十次比较，四叉树的递归 + 每帧重建在 GDScript 里反而更贵。
2. **Godot 的物理引擎已经做了广相**。射线查询、`Area3D` 重叠、碰撞检测都走引擎的 broadphase，你自己再叠一层四叉树不会加速这些。
3. **真正的开销不在邻居搜索**。当前吞吐约 130 决策步/秒，瓶颈在每物理帧的奖励评估 + 业务逻辑 + 射线，不在遍历。**优化前先 profile**（Godot 的 profiler 按函数耗时排序），别凭直觉优化。
4. **如果将来一定要空间结构**（比如地图扩大到上百乘客、城市级路网）：
   - 用**均匀网格**而不是四叉树：缓存友好、更新 O(1)、无递归、GDScript 里实现代价最低；
   - 或者干脆用 Godot 的 `Area3D` + 碰撞层，让引擎维护；
   - 四叉树在动态对象多、密度差异极大的场景才有优势，你的场景密度均匀。
5. **过渡期的低成本优化**：候选列表（最近乘客、范围内敌人）**每 K 帧更新一次**并缓存，比换数据结构收益大得多。

## 5. 路线图与判定标准

| 阶段 | 内容 | 判定（全部用业务指标） |
|---|---|---|
| **P0**（本周） | 观测契约 v2（扣对手 24 维、加目标 6 维、加队友通道）；回归评测套件 | 单车空场/墙场景成功率不低于现有基线（1.00 / 0.965），掉则回退 |
| **P1** | 倒车专项课程 + 单车行驶策略收敛 | 倒车专项任务倒车占比 >0 且任务完成；常规任务倒车占比仍 <5% |
| **P2** | `vehicles_per_faction` 提到 4–6；info 回传 `(arena, company, slot, alive)`；随机车厢数训练 | 评测能按 (场地, 阵营) 正确分组，掩码无错位 |
| **P3** | 冻结 level-1，训调度器（双塔分数 + 匈牙利；基线 = 最近乘客 + 预约锁） | 平均等待时间或送达数 ≥ 基线；**分配达成率** > 0.8 |
| **P4** | 加 CLS query 全局注意力 | 相对 P3 同判据同种子有增益 |
| **P5** | 炮台（脚本敌人）：索敌算法 + 目标选择学习 | 目标选择优于"打最近敌人"脚本基线；误伤率低 |
| **P6** | 变长泛化 / 自博弈 / 论文实验补全 | 评审能复现 |

**每阶段的纪律**（沿用已验证的做法）：任何成功率必须带判据 + 阵营数 + 并行智能体数；奖励值不作为验收；改场景参数后必须重启场景；训练/评估/演示同配置同步长。

## 6. 风险表

| 风险 | 触发信号 | 对策 |
|---|---|---|
| 扣掉对手观测后墙场景退化 | P0 墙场景成功率明显低于 0.965 | 保留 2 个最近车辆槽位（只 8 维）作为折中 |
| agent 顺序隐性依赖被打破 | 分组错位、调度指令发给了错误的车 | 顺序与掩码全部走 `info`，并加断言校验（数量和 alive 位对得上） |
| 阵营车辆数太少导致调度无差异 | P3 学出来的分数与"离得近"高度秩相关 | 提到 4–6 车并随机化；补任务 token 特征（等待时长、被抢风险） |
| 层次化非平稳，两层一起训崩 | 分配达成率掉、团队回报震荡 | 坚持"冻结 level-1 只训调度器"；联合微调是加分项不是主线 |
| 炮台引入后行驶策略退化 | 行驶任务成功率下降 | 炮台奖励权重从 0 起步、逐档加；先单独训炮台头再联合 |
| 超算上跨进程调度 | 同阵营车辆分布在不同进程 | 场地→进程的分配规则保证同阵营同进程（在 `n_parallel` 划分时定死） |
